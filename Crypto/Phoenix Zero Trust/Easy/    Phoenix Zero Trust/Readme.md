## Source Code Analysis

### The Protocol (`main.rs`)

The server implements the standard **Schnorr identification scheme**:

```
1. Prover  → sends commitment  u = g^r mod p
2. Verifier → sends challenge   c  (random)
3. Prover  → sends response    z = r + c·x mod q
4. Verifier → checks           g^z ≡ u · h^c  (mod p)
```

where `h = g^x mod p` is the user's public key and `x` is the private key (the witness).

The parameters use the **RFC 7919 2048-bit safe prime**:

```rust
fn schnorr_params() -> (BigUint, BigUint, BigUint) {
    let p = BigUint::from_str_radix("FFFFFFF...FFFFFFF", 16).unwrap();
    let q = (&p - BigUint::one()) >> 1;   // (p-1)/2
    let g = BigUint::from(2u32);
    (p, q, g)
}
```

### The Critical Bug — Fake CSRNG

```rust
use rand_mt::Mt as CSRNG;          // ← aliased to look cryptographically secure
...
let mut rng = CSRNG::from_entropy(); // initialized once at startup
...
fn schnorr_challenge(p: &BigUint, rng: &mut CSRNG) -> BigUint {
    rng.gen_biguint_range(&BigUint::one(), p)  // same rng shared for ALL logins
}
```

`rand_mt::Mt` is **MT19937 — Mersenne Twister**, one of the most well-known non-cryptographic PRNGs. The `CSRNG` alias is pure misdirection. Key properties that make this exploitable:

- The internal state is only **19968 bits (624 × 32-bit words)**
- Given **624 consecutive 32-bit outputs**, the entire state can be fully recovered
- All future (and past) outputs become predictable

## Vulnerability

### Why Schnorr is "Simulatable"

The Schnorr protocol is **perfect zero-knowledge**, which has a subtle implication: for any challenge `c`, a *simulator* can construct a valid transcript `(u, c, z)` **without knowing the private key `x`**, as long as it can choose `c` freely before committing to `u`.

The simulator works backwards:

```
1. Pick random z  ∈ [1, q)
2. Pick random c  (the challenge we want to use)
3. Compute u = g^z · (h^c)⁻¹  mod p
```

Verification always passes because by construction:
```
g^z ≡ u · h^c  (mod p)
```

The catch in the real protocol is that the **verifier chooses `c` after seeing `u`**, so the prover cannot fake it. **But if we can predict `c` before sending `u`, we break the protocol entirely.**

### Combining Both Weaknesses

Since `c` is generated by a predictable MT19937:

1. Observe enough challenges to recover the MT state
2. Predict the *next* `c` before sending any commitment `u`
3. Use the simulator to forge a valid `(u, z)` pair for that `c`
4. Authenticate as `overwatch` with no knowledge of `x`

## Exploitation

### Phase 1 — Harvesting MT Output

The server generates challenges via:

```rust
rng.gen_biguint_range(&BigUint::one(), p)
```

Internally this does:
```
raw = 64 consecutive MT u32 outputs assembled little-endian
c   = (raw % (p - 1)) + 1
```

So to recover the raw MT words from an observed challenge:
```python
raw = c - 1                      # undo the +1
for _ in range(64):
    outs.append(raw & 0xFFFFFFFF)  # extract lowest 32 bits
    raw >>= 32                     # shift to next word
```

We trigger 10 dummy logins (sending invalid inputs to fail auth — we only care about `c`):

```python
for i in range(10):
    conn.sendlineafter(b"> ", b"2")
    conn.sendlineafter(b"Username: ", b"overwatch")
    conn.sendlineafter(b"Commitment u (g^r mod p): ", b"1")
    conn.recvuntil(b"Challenge c: ")
    c = int(conn.recvline().strip().decode())
    conn.recvuntil(b"Response z")
    conn.sendline(b"1")   # dummy — will fail
    conn.recvline()

    c -= 1                         # KEY: recover raw MT value
    for _ in range(64):
        outs.append(c & 0xFFFFFFFF)
        c >>= 32
```

10 challenges × 64 words = **640 raw u32 values** (we need 624).

### Phase 2 — Cloning MT State with `randcrack`

Feed the first 624 words into `randcrack` to reconstruct the full MT internal state, then advance past the extra 16 words to sync position with the server:

```python
from randcrack import RandCrack

rc = RandCrack()
for i in range(624):
    rc.submit(outs[i])
for i in range(624, len(outs)):
    rc.predict_getrandbits(32)   # consume extras to sync position
```

### Phase 3 — Predicting the Next Challenge

```python
next_c = rc.predict_randint(1, P - 1)
```

`predict_randint(1, P-1)` mirrors exactly what `gen_biguint_range(1, p)` does under the hood — same algorithm, same output.

### Phase 4 — Forging the Schnorr Proof

Retrieve the public key `h` from the server's user list, then run the simulator:

```python
# get h from server
conn.sendlineafter(b"> ", b"3")
conn.recvuntil(b"overwatch: ")
pubkey = int(conn.recvline().strip().decode())

c = next_c
z = random.randint(1, (P - 1) // 2 - 1)
u = pow(G, z, P) * pow(pow(pubkey, c, P), -1, P) % P
```

Send `u`, receive `c` (matches prediction), send `z` → authentication passes, flag printed.

## Why the Exploit Works — Math Summary

The Schnorr verifier checks: `g^z ≡ u · h^c (mod p)`

We construct `u` to satisfy this identity for our chosen `z` and predicted `c`:

```
u = g^z · (h^c)⁻¹  mod p

Verification:
  u · h^c = g^z · (h^c)⁻¹ · h^c = g^z  ✓
```

No discrete log is needed. The only requirement is knowing `c` before committing to `u` — which MT state recovery provides.

## Key Takeaways

| Mistake | Impact |
|---|---|
| Using MT19937 (`rand_mt`) for cryptographic challenges | Full state recovery after 624 outputs |
| Aliasing it as `CSRNG` | Misleads code reviewers |
| Single RNG instance shared across all sessions | Outputs form a continuous recoverable stream |
| Schnorr protocol is simulatable | Any predictable challenge breaks auth entirely |

**Fix:** Replace `rand_mt::Mt` with a cryptographically secure RNG such as `rand::rngs::OsRng` or `ChaCha20Rng`. The Schnorr protocol itself is sound — only the RNG is broken.
